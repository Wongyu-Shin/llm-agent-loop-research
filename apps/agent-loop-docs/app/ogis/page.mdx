  <Section id="checkpoint" title="LLM이 patch 후보를 만들면 harness가 test와 compiler로 후보를 확인합니다">
    결제 API를 고칠 수 있는 patch는 여러 개입니다. 계산 결과를 clamp할 수도 있고, `discount < 0`만 검사할 수도 있으며, `discount > subtotal`까지 함께 거부할 수도 있습니다. LLM은 이 candidate space에서 patch를 제안하는 learner로 볼 수 있습니다.

    Harness는 compiler, unit test, contract test를 호출합니다. 결과를 다음 prompt나 작업 memory에 남기면 다음 learner 호출은 이전과 다른 evidence를 받습니다.

    <LeadStatement>
      OGIS가 묻는 핵심은 “몇 번 다시 생성했는가”가 아니라 “어떤 응답이 어떤 후보를 탈락시켰는가”입니다.
    </LeadStatement>
  </Section>

  <Section id="oracle-interface" title="OGIS의 oracle은 query와 response type이 정해진 검증 interface입니다">
    OGIS의 oracle은 막연한 전문가 비유가 아닙니다. Learner가 보낼 query와 oracle이 돌려줄 response type이 정해져 있습니다. Code agent에서는 다음 interface가 그 구조를 보여줍니다.

    <OgisProtocolExplorer />

    ```ts
    type VerificationResult =
      | { kind: "accept" }
      | {
          kind: "counterexample"
          input: { subtotal: number; discount: number }
          expected: "accept" | "reject"
        }

    type Verify = (patch: Patch) => Promise<VerificationResult>
    ```

    `fail` 한 단어보다 실패 입력과 기대 동작이 더 많은 후보를 구분합니다. 반대로 자연어 review가 모호하거나 test가 실제 요구사항과 어긋나면 oracle 응답도 잘못된 방향으로 후보를 줄일 수 있습니다.
  </Section>

  </Section>

  <Section id="lab" title="할인값을 질의할 때마다 계약과 모순되는 validation 후보가 탈락합니다">
    <OgisOracleLab />

    실습의 target은 `0 ≤ discount ≤ subtotal`인 요청만 허용하는 규칙입니다. Learner는 현재 evidence와 일관된 첫 validation 후보를 냅니다. Membership query는 선택한 할인값의 label을 알려 주고, equivalence query는 현재 후보를 깨는 할인값을 돌려줍니다.
  </Section>

  <Section id="formal-model" title="누적 evidence와 일관된 후보만 version space에 남습니다">
    Candidate class를 $C$, 누적 evidence를 $E_t$라고 합시다. 현재 version space는 evidence와 일관된 후보의 집합입니다.

    $$
    C_t=\{c\in C\mid c\text{ is consistent with }E_t\}
    $$

    한 번의 OGIS step은 learner, oracle, memory update로 나눌 수 있습니다.

    $$
    c_t=\operatorname{Learn}(E_t),\qquad
    r_t=\operatorname{Oracle}(q_t,c_t),\qquad
    E_{t+1}=\operatorname{Update}(E_t,r_t)
    $$

  </Section>

  <Section id="agent-boundary" title="Candidate와 typed oracle query가 있을 때 OGIS 설명이 성립합니다">
    LLM은 program, plan, answer를 제안할 수 있습니다. Harness가 oracle을 호출하고 응답을 context, 파일, memory에 남기면 다음 호출의 proposal distribution은 달라집니다.

    $$
    x_t=\operatorname{Decode}(P_\theta(\cdot\mid g,H_t)),\qquad
    f_t=\operatorname{Oracle}(g,x_t),\qquad
    H_{t+1}=U(H_t,x_t,f_t)
    $$

    <OgisApplicabilityLens />

    <Note label="동일시하지 않기" tone="warn">
      <p>Scalar score만 받는 실험 loop는 black-box optimization에 더 가깝습니다. 환경 observation을 받아 다음 action을 고르는 문제는 POMDP가 더 잘 설명합니다. OGIS는 candidate와 oracle query가 구현에서 식별될 때 유용합니다.</p>
    </Note>

    LLM과 OGIS를 직접 연결한 연구도 있습니다. MILCOM 2023 연구는 LLM plan을 Z3로 검사하고 counterexample을 다음 prompt에 넣었습니다. NeurIPS 2024의 LLMLift는 방법을 `LLM-based OGIS`라고 부르며 LLM이 만든 program summary와 invariant를 verifier로 확인합니다.
  </Section>
